# 3D: `libbmds3d`, software 3D for programs

Status: **step 1 built** (2026-11-06; planned the same day with the user). First user: BMDS Demo #1 (`demo.md`); built so
any program (games, preso's scenes, angel scripts later) can draw 3D the same way.

## 1. Goal

- **3D drawing in the SDK** (the user's: as much as possible in the kernel or the SDK, so others
  can build with these tools): wireframe first, then flat, Gouraud and textured solids.
- **Our own small API, not OpenGL** (decided with the user, 2026-11-06, §2).
- **Fast at the demo's size:** 640×360 L8 at 60 fps on one core, with the palette tricks 8-bit
  makes possible (shade ramps, light tables, saturating additive blending).
- Drawing onto the canvases programs already have (`bmds_canvas_t`, `bmds/game.h`), so 2D and
  3D mix freely: a canvas can be a texture, a 3D object can be drawn over a 2D effect.

## 2. Decisions (the user's, 2026-11-06)

- **Not OpenGL.** There is no GPU for it to front. GL is a float state machine whose semantics
  (perspective-correct texturing, blend modes, a depth test on every fragment) cost exactly what
  a software renderer can't afford, and its surface is large: under Prime Directive 1 we would
  freeze all of it. TinyGL (a GL 1.x subset) was considered and passed over: RGB-only and float
  in its inner loops, so it throws away L8 and PIE. A GL-flavoured layer can sit on top later.
- **In the SDK, not the kernel.** There is no 3D hardware to arbitrate, so a kernel rasterizer
  would only add system-call cost and grow the syscall table. The kernel does what needs it:
  surfaces, presenting, the 2D-DMA (`games.md` §3, §25), and frame timing (§9, K1). The library
  is a static archive (`libbmds3d.a`), linked like `libbmdsgame`; only what a program calls is
  linked in.
- **No binary ABI, as libbmdsgame:** a static library has no system calls of its own, and a
  program keeps the version it was built with (`game.h`'s own statement). Source compatibility is
  still kept: structs that callers fill begin with `uint32_t size`, flags reject unknown bits, and
  the API grows by appending. Kept small all the same.
- **The style is GL's where knowledge transfers:** column-major matrices, right-handed view space
  looking down −Z, counter-clockwise front faces, `perspective()` and `look_at()` as GLU's. Other
  than that, the API is a handful of calls on meshes and materials.

## 3. Facts that shape the design (checked 2026-11-06)

- **The FPU is single precision** (both HP cores), but **PIE has no float vectors**
  (`docs/platforms/esp32p4.md` §1). So transforms, lighting and clipping are per-vertex floats;
  everything per pixel is integer fixed point, PIE where it fits.
- **The budget:** 640×360 is 230,400 pixels; at 400 MHz and 60 fps a core has ~6.7 M cycles a
  frame, ~29 per pixel. A 2D effect touching every pixel (plasma, tunnel) takes a good share;
  3D adds its spans over it.
- **The canvas is in PSRAM** (the surface's buffers; `BMDS_SURFACE_FAST` takes only small ones,
  Doom's 64 KB). PSRAM is ~70 MB/s for copy-like loops through the cache (`esp32p4.md`); rows
  written left to right are the cheap order, columns thrash. Spans are rows.
- **The canvas has damage** (`BMDS_CANVAS_MAX_DAMAGE`): 3D draws mark their bounding boxes so a
  frame presents only what changed. A demo usually repaints everything (`bmds_canvas_damage_all`).
- **The L8 palette is set per present** (`BMDS_SURFACE_PALETTE`), so shade ramps and light tables
  can be rebuilt or cycled any frame.
- **Saturating byte adds are PIE's own** (`esp.vadd.u8` saturates on v2p1): additive glow in L8
  is one instruction per 16 pixels when the palette is laid out as ramps.

## 4. The model

### 4a. Coordinates and math (`bmds_vec3_t`, `bmds_mat4_t`)

- `bmds_vec3_t {float x, y, z}`, `bmds_vec4_t`, `bmds_mat4_t {float m[16]}` column-major.
- Small inline helpers in the header (add, sub, scale, dot, cross, length, normalize) and
  functions for matrices: `identity`, `multiply`, `translate`, `scale`, `rotate_x/y/z`,
  `rotate(axis, angle)`, `perspective(fovy, aspect, near, far)`, `ortho`, `look_at`,
  `invert_affine`, `transform_point`, `transform_vector`. Angles in radians.
- A quaternion type later if the demo's camera wants slerp (not in step 1).

### 4b. The context (`bmds_3d_t`)

One per drawing thread, opaque, made by `bmds_3d_create(const bmds_3d_config_t *config,
bmds_3d_t **out)` and freed by `bmds_3d_destroy()`. The config names the most triangles queued in
a frame (its scratch memory is allocated once here, nothing per frame) and the memory flags
(`BMDS_MEM_FAST` for the scratch, when it fits).

It holds:

- **The target:** a `bmds_canvas_t *` (`bmds_3d_set_target`), its clip rectangle the viewport's
  limit. Two contexts with two bands of the same canvas draw on two cores (§7).
- **The viewport:** where normalized device coordinates land (`bmds_3d_set_viewport`).
- **Matrices:** projection, view, and a model stack (16 deep: `push`, `pop`, `load`, `mult`).
- **Lights:** an ambient level and up to 4 directional or point lights (step 3).
- **The colour mapping** for the target's format (§5).
- **An optional z-buffer** (§4e) and the scratch for the frame's queue.
- **Counters:** triangles in, culled, clipped, drawn, pixels drawn, the last frame's time; read
  with `bmds_3d_stats()` for the demo's overlay and for benches.

### 4c. Meshes (`bmds_3d_mesh_t`)

A caller-filled struct (size first) of plain arrays, so models can be static rodata:

- `positions` (xyz floats), optional `normals`, `uvs` (floats 0..1, wrapped), `colors` (a ramp or
  pixel per vertex);
- `indices` (uint16 triangles, counter-clockwise front);
- optional `edges` (uint16 pairs) for wireframe, since a triangulated quad's diagonal isn't an
  edge anyone wants to see; `bmds_3d_mesh_edges()` derives them from triangles, dropping edges
  between coplanar faces;
- `vertex_count`, `triangle_count`, `edge_count`, and a bounding sphere (for culling a whole
  mesh; computed by `bmds_3d_mesh_bounds()`).

**Generators** (`bmds_3d_mesh_make(kind, params, mem_flags, &mesh)`, freed by
`bmds_3d_mesh_free`): cube, plane grid, UV sphere, icosphere, cylinder, cone, torus, torus knot
(p, q), and an extruded 2D polygon (logos). Normals included; smooth or faceted by a flag.

**Loading** (step 5): Wavefront OBJ (positions, normals, uvs, faces triangulated), so people can
bring models from any modeller.

### 4d. Materials (`bmds_3d_material_t`)

Caller-filled (size first):

- `mode`: `POINTS`, `WIRE`, `FLAT`, `GOURAUD`, `TEXTURED`, `TEXTURED_FLAT` (textured and lit per
  face), `TEXTURED_GOURAUD`, `ENVMAP` (uvs from view-space normals: chrome).
- `color`: a pixel (wire, points, unlit flat) or a ramp (§5a) for lit modes.
- `texture`: a `bmds_game_image_t` (any canvas can be wrapped as one, so last frame's plasma is
  this frame's texture); power-of-two sizes for wrapping by mask.
- `flags`: `CULL_BACK` (default), `CULL_FRONT`, `DEPTH_TEST`, `DEPTH_WRITE`, `ADD` (L8:
  saturating add of the index's offset in its ramp; RGB: per channel), `DEPTH_CUE` (shade by
  distance: fog to the ramp's dark end).

### 4e. Drawing and visibility

- `bmds_3d_begin(ctx)` … `bmds_3d_draw(ctx, mesh, material)` … `bmds_3d_end(ctx)`: draws are
  transformed, lit, clipped and queued at `draw`; `end` sorts the frame's queue far to near (a
  radix sort on 16-bit depth) and rasterizes (the painter's algorithm). Demo scenes are mostly
  convex objects apart from each other: the sort is enough and costs no memory per pixel.
- **The z-buffer is optional** (`bmds_3d_set_depth(ctx, buffer)`, 16 bits, the caller's memory or
  the context's): draws with `DEPTH_TEST` rasterize at once in draw order, testing per pixel.
  At 640×360 it is 460 KB of PSRAM traffic to clear and to read each frame, so it is for scenes
  that need it (intersecting objects), measured before it is recommended (§10).
- **Immediate draws** without a queue: `bmds_3d_lines()` (a strip or pairs of 3D points),
  `bmds_3d_points()` (stars: a pixel or a small disc sized by depth), and
  `bmds_3d_project()` (points to screen x, y and depth for the caller's own drawing: vector balls,
  sprites, labels), with `bmds_3d_sort_depth()` to order them.

### 4f. The pipeline

1. **Cull the mesh** by its bounding sphere against the frustum.
2. **Transform** positions by model-view-projection (float, per vertex, in the scratch); normals
   by the model-view's rotation for lighting.
3. **Light** per vertex (`GOURAUD`) or per face (`FLAT`): ambient + Σ lights' `max(0, n·l)`,
   to an intensity 0..1, then to a shade index in the material's ramp.
4. **Back-face cull** on the projected winding (after clipping is decided, before rasterizing).
5. **Clip** in homogeneous space against near (always) and far; x and y are handled by a guard
   band (screen coordinates within ±8× the viewport are rasterized and span-clipped; beyond that
   the triangle is clipped against the side planes). Clipping makes up to 7 vertices per triangle.
6. **Rasterize**: screen positions in 28.4 fixed point, the top-left fill rule (shared edges
   draw each pixel once: no cracks, no double-drawn pixels, which matters for `ADD`), edges
   stepped per row with exact sub-pixel prestep, spans handed to the mode's span function.
7. **Spans**: one function per (mode × format), each a tight loop. Interpolants (shade, u, v,
   depth) are 16.16 fixed point stepped per pixel; texturing is affine per triangle (the
   PS1-style swim is part of the look) with an optional perspective correction every 16 pixels
   (Quake's way) as a flag in step 4.

## 5. Colour per format

### 5a. L8: ramps and tables

The palette is the material. A **ramp** is a run of palette entries from dark to bright
(`bmds_3d_ramp_t {first, count}`); lit modes map intensity 0..1 to `first + i·(count−1)`, and
Gouraud interpolates the index (8.8 fixed) along the span. A 256-entry palette holds, for
example, 8 ramps of 32 or 16 of 16; palette helpers make them (`bmds_palette_ramp()`, §8).

**Textured and lit in L8** needs a **light table** like Doom's COLORMAP: `table[shade][texel]` →
the palette index nearest to that texel's colour at that light. 32 shades × 256 = 8 KB, built from
the palette by `bmds_3d_light_table()` (nearest colour by a 32³ cube lookup, a few ms), rebuilt
when the palette changes enough to matter (the demo builds its tables once per part).

`ADD` in L8 adds the shade's offset within its ramp and saturates at the ramp's top: glow lines,
particles and light beams on a black ramp background. With a single 256-entry ramp it is PIE's
saturating `vadd` exactly.

### 5b. RGB565 and BGR24

Wire, points and unlit flat work in every format from step 1 (a pixel value). Lit and textured
modes in RGB565 come in step 6 (shading by multiply per channel); BGR24 only if a program asks.
The demo is L8, so L8 comes first in every step.

## 6. SIMD (PIE)

Per `simd.md`'s rule, every PIE kernel has a scalar twin it matches byte for byte, tested on the
host (scalar) and by `simd test` on the board.

- **Flat spans:** 16 bytes per store once aligned (libbmdsgame's fill already does it).
- **Gouraud L8:** 16 indices per step from two 8-lane 16-bit vectors (`base + lane·step`, then
  `+= 16·step`), shifted and narrowed to bytes. Spans under 16 pixels stay scalar.
- **`ADD`:** load 16, saturating add a vector, store.
- **Z-test** (step 4, if the z-buffer earns its place): 8 lanes of 16-bit compare and select.
- **Texture fetches** don't vectorize (gathers); the texel loop is scalar and unrolled, with the
  texture in internal RAM when it fits (`BMDS_MEM_FAST`: a 64×64 L8 texture is 4 KB).

## 7. Two cores

The context is single-threaded. A program wanting both cores makes two contexts on the same
canvas, each with its own band (`bmds_canvas_set_clip`), and draws the same scene in both; vertex
work is repeated (cheap next to spans) and no locks are taken. The demo measures whether its
second core is worth it beside the display's work (`demo.md` §8).

## 8. What goes in `libbmdsgame` beside it

Pieces 2D effects and 3D share, useful to any program (`games.md` §1: what programs share is in
the SDK):

- **Palette helpers** (`bmds/palette.h`): ramps (`bmds_palette_ramp(rgb, first, count, from,
  to)`, through a midpoint, HSV), fades between palettes and to a colour, cycling a range,
  flashes; and `bmds_game_palette()` to set the loop's surface palette on the next present.
- **Texture mapping a whole canvas:** an affine map with wrapping (`bmds_canvas_texture_affine`:
  rotozoomers, floors) and a lookup-table map (`bmds_canvas_remap`: per-pixel (u, v) tables, for
  tunnels and lens effects), both PIE-assisted where they can be.
- **Canvas as an image:** `bmds_canvas_image()` wraps a canvas as a `bmds_game_image_t` (a
  texture, a feedback blit).

Which of the demo's effects graduate to the SDK is decided per effect in `demo.md` §6.

## 9. Frame timing (kernel, K1)

Beat sync (`sequencer.md`) needs to know **when a presented frame is seen**. `surface_present`
returns the frame number it will be shown in; `BMDS_SURFACE_INFO` counts `frames` begun but has no
time. **ABI (appended):** `bmds_surface_info_t` gains `frame_ns` (`BMDS_CLOCK_MONOTONIC` when
frame `frames` began) and `frame_period_ns`; so frame N is shown at `frame_ns + (N − frames) ×
frame_period_ns`. `bmds_game_frame_ns(game)` in the loop returns the time the frame being drawn
will be shown. This is the only kernel piece 3D needs; it belongs to the sequencer's sync more
than to 3D, and is built in the sequencer's step 1.

## 10. Budgets and measurements

- **Code:** the library ~25-35 KB of text linked whole; a program using wire and flat only links
  less (one object per mode family). Not in the firmware at all.
- **Memory:** a context's scratch: per queued triangle ~32 bytes plus transformed vertices
  (~24 bytes each); 4,096 triangles ≈ 230 KB in PSRAM, or a small queue in internal RAM.
- **Targets on the board** (640×360 L8, one core, measured in step 2-4 benches, recorded here):
  - wireframe: 5,000 edges a frame at 60 fps;
  - flat: 3,000 triangles of ~150 px;
  - Gouraud: 2,000 triangles of ~150 px;
  - textured: 1,000 triangles of ~200 px.
  These are guesses to be replaced by the benches' numbers; the design changes if they are far
  off (spans in IRAM, the queue in internal RAM, two cores by default).
- **Benches** in the system benchmark (`bench.md`): `3d.wire`, `3d.flat`, `3d.gouraud`,
  `3d.textured`, `3d.zbuffer`, scalar and PIE, from `benchprog`'s descriptor.

## 11. Testing

- **Host (doctest, `tests/host/3d.cpp`):** the math (against worked values), clipping (every
  vertex on the right side, interpolants continuous), the fill rule (a fan of triangles around a
  point and a grid of quads cover each pixel exactly once: counted with `ADD` on a zero canvas),
  culling, the sort, golden checksums of small renders per mode and format, the light table's
  nearest colours.
- **Fuzzing** (`tests/fuzz`): the OBJ loader, and the rasterizer on random (huge, degenerate,
  NaN) triangles: nothing written outside the clip.
- **The board:** the benches; `sdk/examples/wire` (a spinning wireframe cube and torus, the
  mouse turning them) and `sdk/examples/solids` (every mode side by side, a key to cycle the
  format); `simd test` for the PIE twins.

## 12. Steps

1. **Math and wireframe:** `bmds/3d.h` (math, context, meshes, materials as designed, modes beyond
   wire refused with `BMDS_ENOSYS` until built), transform, clip, project, `WIRE` and `POINTS`,
   `bmds_3d_lines/points/project`, the cube, grid, sphere and torus generators, edges; host tests;
   `wire` example; `3d.wire` bench.
2. **Solids:** the rasterizer with the fill rule, `FLAT` and `GOURAUD` in L8 (scalar), the queue
   and sort, lighting, ramps; palette helpers in libbmdsgame (§8); `solids` example; benches.
3. **PIE** for the L8 spans, measured against scalar; the remaining generators (torus knot,
   cylinder, cone, icosphere, extrusion).
4. **Textures:** `TEXTURED*` and `ENVMAP` in L8, light tables, canvas as texture, the perspective
   flag; the optional z-buffer and its bench (kept only if it earns its place).
5. **OBJ loading**, fuzzed.
6. **RGB565** lit and textured modes.
7. **angel bindings** (`angel`'s graphics module): meshes, materials, a scene in a script.

## 13. As built

### Step 1: math and wireframe (2026-11-06)

- **`sdk/include/bmds/3d.h`, `sdk/3d/`** (`libbmds3d.a`, linked by `bmds_add_program` and
  `bmds-cc` after libbmdsgame): `math.c` (the matrices), `mesh.c` (shapes, edges, bounds),
  `context.c` (contexts, the stack, culling, drawing meshes, projecting, sorting, counters),
  `wire.c` (segments and points). 15.8 KB of text in all (math 2.2, meshes 5.4, contexts 4.6,
  wire 3.6); a program links only the objects it uses.
- **As designed in §4, with these settled:**
  - The vertex scratch is the context's only memory (28 bytes a vertex, 4,096 by default:
    112 KB; `BMDS_MEM_FAST` falls back to PSRAM when internal RAM can't hold it).
  - **Edges:** vertices at one position are welded (a hash on the positions' bits), the
    triangles' sides sorted (an LSD radix sort on the welded pair), each run one edge with its
    first two triangles. Made shapes **mark their quads' diagonals** as they make them (exact: a
    sphere's or torus's quads aren't planar, and a grid's lines and diagonals are both between
    coplanar triangles); where one of a quad's triangles has no area (a sphere's poles) the
    other's "diagonal" is a real edge and isn't marked. A caller's mesh gets the heuristic:
    dropped between coplanar triangles when it is the longest side of both, or every coplanar
    edge with `BMDS_3D_EDGES_COPLANAR` (a fan, a cap). `owned_edges` beside `owned`, so a made
    mesh's edges can be rebuilt without freeing its geometry.
  - **Hidden lines** (`BMDS_3D_CULL_BACK` on wire): an edge is drawn when either triangle beside
    it faces the viewer, tested in view space (`n · p < 0`; looking down −Z for an orthographic
    projection), so it works with the eye inside the bounds and through near clipping. Exact for
    convex meshes; a torus shows its inner far side, as expected without a depth test.
  - **Segments:** near and far clipped in clip space (Liang and Barsky), projected, clipped to the
    viewport within the canvas's clip, then stepped along the major axis in 16.16 from the exact
    sub-pixel ends: the pixels whose centres the line passes, each end's pixel included, the
    minor coordinate clamped to the ends' rows (no stray pixel past an end). The shade is
    stepped beside it, so a line going away fades along its length.
  - **Shades:** one table of pixel values a draw (`bmds_3d_ink_t`): the ramp's entries on L8,
    32 levels of `rgb` towards black on RGB565 and BGR24, so the inner loops are the same for
    every format.
  - **Points** are `point_size` squares, centred, culled by the clip volume.
  - Fog defaults to 1-100; `bmds_3d_stats()` counts meshes, culled meshes, vertices, lines,
    points and pixels since `bmds_3d_begin()`.
- **Host tests** (`tests/host/3d.cpp`, 9 cases, 12,809 assertions): the matrices against worked
  values, GLU's perspective and look-at; made meshes' edge counts (cube 12, grid 2n(n+1) with
  4n open, sphere's meridians and parallels with the seam welded, torus closed) and outward
  faces; a caller's square and hexagon fan; lines on exact pixels (horizontal, diagonal, a
  strip), damage; clipping in all three formats, with 4,000 random huge lines, orthographic and
  through the eye, and a NaN, never writing outside the clip; near clipping; points; shading by
  distance on L8 and BGR24; a wire cube's 12 edges, 4 head-on and 9 at a corner with hidden lines,
  culled whole behind the camera; `ENOSYS`, `ENOSPC`, bad flags; the stack; projecting and
  sorting; no allocation left (`FakeMemory`, the host's `mem_alloc` and `mem_free`, now in the
  fake system call table libbmdsgame's tests use).
- **`sdk/examples/wire`**: the stars, a cube, a torus and an orbiting sphere at 640×360 L8, the
  mouse turning the camera, the wheel moving it, Space for hidden lines, `-F` full screen, `-e`
  nothing but the clear (what presenting costs). Checked on the board, windowed and full screen.
- **`render.wire` in `benchprog`** (`benchprog wire`), the board, 640×360 L8 in PSRAM:

  | Case | ms a frame |
  |---|---|
  | cube, torus (32×12), sphere (12×8), hidden lines | 2.37 |
  | the same, all 960 edges | 3.17 (3.3 µs an edge) |
  | 2,000 points, shaded | 1.90 (0.95 µs a point) |

  §10's target of 5,000 edges a frame needs about three times this; the time is mostly per edge
  (clipping and projecting each end again, the shade, the face tests), not per pixel. Projecting
  each vertex once into the scratch and reusing it, and the face tests cached per triangle, come
  with step 2's queue.
- **Found: presenting is the limit, not drawing.** `wire` runs at 35-37 fps windowed or full
  screen, drawing in 7-8 ms; `wire -e` (a clear and the counters, 3 ms) runs at 38-39. A
  640×360 L8 surface damaged whole every frame presents at under 40 a second (games.md's
  measurements agree: 39 for RGB565 at 2× full screen, damaged whole). The demo draws whole
  frames, so this is the first thing it needs from the kernel (`demo.md` §8a). Fixed the same day
  (`demo.md` §8b, `games.md` §27): `wire -F` now runs at 60.
