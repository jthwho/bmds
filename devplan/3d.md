# 3D: `libbmds3d`, software 3D for programs

Status: **steps 1-3 built, step 4 (textures) built and host-tested, not yet measured on the board** (2026-11-07; planned 2026-11-06 with the user). First user: BMDS Demo #1 (`demo.md`); built so
any program (games, preso's scenes, angel scripts later) can draw 3D the same way.

## 1. Goal

- **3D drawing in the SDK** (the user's: as much as possible in the kernel or the SDK, so others
  can build with these tools): wireframe first, then flat, Gouraud and textured solids.
- **Our own small API, not OpenGL** (decided with the user, 2026-11-06, §2).
- **Fast at the demo's size:** 640×360 L8 at 60 fps on one core, with the palette tricks 8-bit
  makes possible (shade ramps, light tables, saturating additive blending).
- Drawing onto the canvases programs already have (`bmds_canvas_t`, `bmds/game.h`), so 2D and
  3D mix freely: a canvas can be a texture, a 3D object can be drawn over a 2D effect.

## 2. Decisions (the user's, 2026-11-06)

- **Not OpenGL.** There is no GPU for it to front. GL is a float state machine whose semantics
  (perspective-correct texturing, blend modes, a depth test on every fragment) cost exactly what
  a software renderer can't afford, and its surface is large: under Prime Directive 1 we would
  freeze all of it. TinyGL (a GL 1.x subset) was considered and passed over: RGB-only and float
  in its inner loops, so it throws away L8 and PIE. A GL-flavoured layer can sit on top later.
- **In the SDK, not the kernel.** There is no 3D hardware to arbitrate, so a kernel rasterizer
  would only add system-call cost and grow the syscall table. The kernel does what needs it:
  surfaces, presenting, the 2D-DMA (`games.md` §3, §25), and frame timing (§9, K1). The library
  is a static archive (`libbmds3d.a`), linked like `libbmdsgame`; only what a program calls is
  linked in.
- **No binary ABI, as libbmdsgame:** a static library has no system calls of its own, and a
  program keeps the version it was built with (`game.h`'s own statement). Source compatibility is
  still kept: structs that callers fill begin with `uint32_t size`, flags reject unknown bits, and
  the API grows by appending. Kept small all the same.
- **The style is GL's where knowledge transfers:** column-major matrices, right-handed view space
  looking down −Z, counter-clockwise front faces, `perspective()` and `look_at()` as GLU's. Other
  than that, the API is a handful of calls on meshes and materials.

## 3. Facts that shape the design (checked 2026-11-06)

- **The FPU is single precision** (both HP cores), but **PIE has no float vectors**
  (`docs/platforms/esp32p4.md` §1). So transforms, lighting and clipping are per-vertex floats;
  everything per pixel is integer fixed point, PIE where it fits.
- **The budget:** 640×360 is 230,400 pixels; at 400 MHz and 60 fps a core has ~6.7 M cycles a
  frame, ~29 per pixel. A 2D effect touching every pixel (plasma, tunnel) takes a good share;
  3D adds its spans over it.
- **The canvas is in PSRAM** (the surface's buffers; `BMDS_SURFACE_FAST` takes only small ones,
  Doom's 64 KB). PSRAM is ~70 MB/s for copy-like loops through the cache (`esp32p4.md`); rows
  written left to right are the cheap order, columns thrash. Spans are rows.
- **The canvas has damage** (`BMDS_CANVAS_MAX_DAMAGE`): 3D draws mark their bounding boxes so a
  frame presents only what changed. A demo usually repaints everything (`bmds_canvas_damage_all`).
- **The L8 palette is set per present** (`BMDS_SURFACE_PALETTE`), so shade ramps and light tables
  can be rebuilt or cycled any frame.
- **Saturating byte adds are PIE's own** (`esp.vadd.u8` saturates on v2p1): additive glow in L8
  is one instruction per 16 pixels when the palette is laid out as ramps.

## 4. The model

### 4a. Coordinates and math (`bmds_vec3_t`, `bmds_mat4_t`)

- `bmds_vec3_t {float x, y, z}`, `bmds_vec4_t`, `bmds_mat4_t {float m[16]}` column-major.
- Small inline helpers in the header (add, sub, scale, dot, cross, length, normalize) and
  functions for matrices: `identity`, `multiply`, `translate`, `scale`, `rotate_x/y/z`,
  `rotate(axis, angle)`, `perspective(fovy, aspect, near, far)`, `ortho`, `look_at`,
  `invert_affine`, `transform_point`, `transform_vector`. Angles in radians.
- A quaternion type later if the demo's camera wants slerp (not in step 1).

### 4b. The context (`bmds_3d_t`)

One per drawing thread, opaque, made by `bmds_3d_create(const bmds_3d_config_t *config,
bmds_3d_t **out)` and freed by `bmds_3d_destroy()`. The config names the most triangles queued in
a frame (its scratch memory is allocated once here, nothing per frame) and the memory flags
(`BMDS_MEM_FAST` for the scratch, when it fits).

It holds:

- **The target:** a `bmds_canvas_t *` (`bmds_3d_set_target`), its clip rectangle the viewport's
  limit. Two contexts with two bands of the same canvas draw on two cores (§7).
- **The viewport:** where normalized device coordinates land (`bmds_3d_set_viewport`).
- **Matrices:** projection, view, and a model stack (16 deep: `push`, `pop`, `load`, `mult`).
- **Lights:** an ambient level and up to 4 directional or point lights (step 3).
- **The colour mapping** for the target's format (§5).
- **An optional z-buffer** (§4e) and the scratch for the frame's queue.
- **Counters:** triangles in, culled, clipped, drawn, pixels drawn, the last frame's time; read
  with `bmds_3d_stats()` for the demo's overlay and for benches.

### 4c. Meshes (`bmds_3d_mesh_t`)

A caller-filled struct (size first) of plain arrays, so models can be static rodata:

- `positions` (xyz floats), optional `normals`, `uvs` (floats 0..1, wrapped), `colors` (a ramp or
  pixel per vertex);
- `indices` (uint16 triangles, counter-clockwise front);
- optional `edges` (uint16 pairs) for wireframe, since a triangulated quad's diagonal isn't an
  edge anyone wants to see; `bmds_3d_mesh_edges()` derives them from triangles, dropping edges
  between coplanar faces;
- `vertex_count`, `triangle_count`, `edge_count`, and a bounding sphere (for culling a whole
  mesh; computed by `bmds_3d_mesh_bounds()`).

**Generators** (`bmds_3d_mesh_make(kind, params, mem_flags, &mesh)`, freed by
`bmds_3d_mesh_free`): cube, plane grid, UV sphere, icosphere, cylinder, cone, torus, torus knot
(p, q), and an extruded 2D polygon (logos). Normals included; smooth or faceted by a flag.

**Loading** (step 5, §12d): models in a binary file of our own (`.bm3d`), laid out as the mesh
struct reads them, so loading is one read and a check; `bmds-mesh3d` on the PC converts Wavefront
OBJ and Bézier patches into it, so people can bring models from any modeller.

### 4d. Materials (`bmds_3d_material_t`)

Caller-filled (size first):

- `mode`: `POINTS`, `WIRE`, `FLAT`, `GOURAUD`, `TEXTURED`, `TEXTURED_FLAT` (textured and lit per
  face), `TEXTURED_GOURAUD`, `ENVMAP` (uvs from view-space normals: chrome).
- `color`: a pixel (wire, points, unlit flat) or a ramp (§5a) for lit modes.
- `texture`: a `bmds_game_image_t` (any canvas can be wrapped as one, so last frame's plasma is
  this frame's texture); power-of-two sizes for wrapping by mask.
- `flags`: `CULL_BACK` (default), `CULL_FRONT`, `DEPTH_TEST`, `DEPTH_WRITE`, `ADD` (L8:
  saturating add of the index's offset in its ramp; RGB: per channel), `DEPTH_CUE` (shade by
  distance: fog to the ramp's dark end).

### 4e. Drawing and visibility

- `bmds_3d_begin(ctx)` … `bmds_3d_draw(ctx, mesh, material)` … `bmds_3d_end(ctx)`: draws are
  transformed, lit, clipped and queued at `draw`; `end` sorts the frame's queue far to near (a
  radix sort on 16-bit depth) and rasterizes (the painter's algorithm). Demo scenes are mostly
  convex objects apart from each other: the sort is enough and costs no memory per pixel.
- **The z-buffer is optional** (`bmds_3d_set_depth(ctx, buffer)`, 16 bits, the caller's memory or
  the context's): draws with `DEPTH_TEST` rasterize at once in draw order, testing per pixel.
  At 640×360 it is 460 KB of PSRAM traffic to clear and to read each frame, so it is for scenes
  that need it (intersecting objects), measured before it is recommended (§10).
- **Immediate draws** without a queue: `bmds_3d_lines()` (a strip or pairs of 3D points),
  `bmds_3d_points()` (stars: a pixel or a small disc sized by depth), and
  `bmds_3d_project()` (points to screen x, y and depth for the caller's own drawing: vector balls,
  sprites, labels), with `bmds_3d_sort_depth()` to order them.

### 4f. The pipeline

1. **Cull the mesh** by its bounding sphere against the frustum.
2. **Transform** positions by model-view-projection (float, per vertex, in the scratch); normals
   by the model-view's rotation for lighting.
3. **Light** per vertex (`GOURAUD`) or per face (`FLAT`): ambient + Σ lights' `max(0, n·l)`,
   to an intensity 0..1, then to a shade index in the material's ramp.
4. **Back-face cull** on the projected winding (after clipping is decided, before rasterizing).
5. **Clip** in homogeneous space against near (always) and far; x and y are handled by a guard
   band (screen coordinates within ±8× the viewport are rasterized and span-clipped; beyond that
   the triangle is clipped against the side planes). Clipping makes up to 7 vertices per triangle.
6. **Rasterize**: screen positions in 28.4 fixed point, the top-left fill rule (shared edges
   draw each pixel once: no cracks, no double-drawn pixels, which matters for `ADD`), edges
   stepped per row with exact sub-pixel prestep, spans handed to the mode's span function.
7. **Spans**: one function per (mode × format), each a tight loop. Interpolants (shade, u, v,
   depth) are 16.16 fixed point stepped per pixel; texturing is affine per triangle (the
   PS1-style swim is part of the look) with an optional perspective correction every 16 pixels
   (Quake's way) as a flag in step 4.

## 5. Colour per format

### 5a. L8: ramps and tables

The palette is the material. A **ramp** is a run of palette entries from dark to bright
(`bmds_3d_ramp_t {first, count}`); lit modes map intensity 0..1 to `first + i·(count−1)`, and
Gouraud interpolates the index (8.8 fixed) along the span. A 256-entry palette holds, for
example, 8 ramps of 32 or 16 of 16; palette helpers make them (`bmds_palette_ramp()`, §8).

**Textured and lit in L8** needs a **light table** like Doom's COLORMAP: `table[shade][texel]` →
the palette index nearest to that texel's colour at that light. 32 shades × 256 = 8 KB, built from
the palette by `bmds_3d_light_table()` (exact nearest colours, 36 ms on the board), rebuilt
when the palette changes enough to matter (the demo builds its tables once per part).

`ADD` in L8 adds the shade's offset within its ramp and saturates at the ramp's top: glow lines,
particles and light beams on a black ramp background. With a single 256-entry ramp it is PIE's
saturating `vadd` exactly.

### 5b. RGB565 and BGR24

Wire, points and unlit flat work in every format from step 1 (a pixel value). Lit and textured
modes in RGB565 come in step 6 (shading by multiply per channel); BGR24 only if a program asks.
The demo is L8, so L8 comes first in every step.

## 6. SIMD (PIE)

Per `simd.md`'s rule, every PIE kernel has a scalar twin it matches byte for byte, tested on the
host (scalar) and by `simd test` on the board.

- **Flat spans:** 16 bytes per store once aligned (libbmdsgame's fill already does it).
- **Gouraud L8:** 16 indices per step from two 8-lane 16-bit vectors (`base + lane·step`, then
  `+= 16·step`), shifted and narrowed to bytes. Spans under 16 pixels stay scalar.
- **`ADD`:** load 16, saturating add a vector, store.
- **Z-test** (step 4, if the z-buffer earns its place): 8 lanes of 16-bit compare and select.
- **Texture fetches** don't vectorize (gathers); the texel loop is scalar and unrolled, with the
  texture in internal RAM when it fits (`BMDS_MEM_FAST`: a 64×64 L8 texture is 4 KB).
- **As measured (§13, efficiency pass, 2026-11-07):** none of it built. Spans average ~7 pixels
  and the time is per row and per triangle; the cuts there (no SIMD) took 8-24% off.

## 7. Two cores

The context is single-threaded. A program wanting both cores makes two contexts on the same
canvas, each with its own band (`bmds_canvas_set_clip`), and draws the same scene in both; vertex
work is repeated (cheap next to spans) and no locks are taken. The demo measures whether its
second core is worth it beside the display's work (`demo.md` §8).

## 8. What goes in `libbmdsgame` beside it

Pieces 2D effects and 3D share, useful to any program (`games.md` §1: what programs share is in
the SDK):

- **Palette helpers** (`bmds/palette.h`): ramps (`bmds_palette_ramp(rgb, first, count, from,
  to)`, through a midpoint, HSV), fades between palettes and to a colour, cycling a range,
  flashes; and `bmds_game_palette()` to set the loop's surface palette on the next present.
- **Texture mapping a whole canvas:** an affine map with wrapping (`bmds_canvas_texture_affine`:
  rotozoomers, floors) and a lookup-table map (`bmds_canvas_remap`: per-pixel (u, v) tables, for
  tunnels and lens effects), both PIE-assisted where they can be.
- **Canvas as an image:** `bmds_canvas_image()` wraps a canvas as a `bmds_game_image_t` (a
  texture, a feedback blit).

Which of the demo's effects graduate to the SDK is decided per effect in `demo.md` §6.

## 9. Frame timing (kernel, K1)

Beat sync (`sequencer.md`) needs to know **when a presented frame is seen**. `surface_present`
returns the frame number it will be shown in; `BMDS_SURFACE_INFO` counts `frames` begun but has no
time. **ABI (appended):** `bmds_surface_info_t` gains `frame_ns` (`BMDS_CLOCK_MONOTONIC` when
frame `frames` began) and `frame_period_ns`; so frame N is shown at `frame_ns + (N − frames) ×
frame_period_ns`. `bmds_game_frame_ns(game)` in the loop returns the time the frame being drawn
will be shown. This is the only kernel piece 3D needs; it belongs to the sequencer's sync more
than to 3D, and is built in the sequencer's step 1.

## 10. Budgets and measurements

- **Code:** the library ~25-35 KB of text linked whole; a program using wire and flat only links
  less (one object per mode family). Not in the firmware at all.
- **Memory:** a context's scratch: per queued triangle ~32 bytes plus transformed vertices
  (~24 bytes each); 4,096 triangles ≈ 230 KB in PSRAM, or a small queue in internal RAM.
- **Targets on the board** (640×360 L8, one core, measured in step 2-4 benches, recorded here):
  - wireframe: 5,000 edges a frame at 60 fps;
  - flat: 3,000 triangles of ~150 px;
  - Gouraud: 2,000 triangles of ~150 px;
  - textured: 1,000 triangles of ~200 px.
  These are guesses to be replaced by the benches' numbers; the design changes if they are far
  off (spans in IRAM, the queue in internal RAM, two cores by default).
- **Benches** in the system benchmark (`bench.md`): `3d.wire`, `3d.flat`, `3d.gouraud`,
  `3d.textured`, `3d.zbuffer`, scalar and PIE, from `benchprog`'s descriptor.

## 12a. Step 2 design: solids (2026-11-06)

- **Lights** (`bmds_3d_light_t`, `bmds_3d_set_light()`, `BMDS_3D_LIGHTS` = 4, `bmds_3d_set_ambient()`):
  directional (towards the light) or point (a position), in world space, or in view space with
  `BMDS_3D_LIGHT_VIEW` (moving with the camera). By default an ambient of 0.25 and light 0
  directional in view space over the viewer's left shoulder at 0.8, so a first solid is lit.
  Lighting is in view space: normals through the model-view's rotation, renormalized (uniform
  scales only). No attenuation yet.
- **Shades:** an intensity 0..1 (ambient plus each light's `max(0, n·l)`, clamped; times the fog
  factor with `BMDS_3D_DEPTH_CUE`) times the ramp's top: 8.8 fixed per vertex. `FLAT` takes the
  triangle's own normal (from its view-space positions: faceted, no normals needed); `GOURAUD`
  the mesh's normals per vertex (none: the face's). `BMDS_3D_UNLIT` (new flag): no lights; the
  material's `pixel`, or with `DEPTH_CUE` the ramp by distance (fog only).
- **Colour per draw:** a draw record, not a 256-entry table a triangle: L8 is `ramp_first +
  shade`; RGB565 and BGR24 look the shade up in 32 levels of `rgb` towards black. Unlit: one
  shade, the pixel. So every format draws every mode from step 2 (RGB at 32 levels; smoother RGB
  in step 6).
- **The queue:** `bmds_3d_draw()` transforms, lights, clips and projects a solid's triangles into
  the context's queue (`max_triangles`, default 2048, 32 bytes each; `max_draws` records, default
  64); `bmds_3d_end()` sorts it far to near (an LSD radix sort on the triangles' mean depth, stable,
  so equal depths keep their order) and draws it. A full queue (or a new target) draws what is
  queued and starts again: never an error. Wire, points and lines still draw at once.
- **Clipping:** Sutherland and Hodgman against near and far, and against the side planes widened
  four times (a guard band: screen coordinates stay within a few viewports, so 28.4 fixed point
  can't overflow; what's outside the viewport but inside the band is cut by the spans). Up to 9
  vertices, fanned into triangles. Back faces culled after projection by the screen winding.
- **The fill rule, exactly:** vertices in 28.4; a row is drawn where its pixel centres' y is in
  [top, bottom); a pixel where its centre's x is in [left edge, right edge). Each edge's first
  pixel column per row is a floor division kept exact by an integer DDA (a quotient and a
  remainder stepped per row; one 64-bit division per edge), and an edge shared by two triangles
  is stepped the same way from the same ends, so they meet without a gap or an overlap.
- **Gouraud spans:** the shade's plane per triangle (float), evaluated at each span's first and
  last pixel centre, both clamped to the ramp, stepped in 16.16 between them.
- **Counters** (appended): triangles queued, back faces, clipped, drawn.

## 12b. Step 3 plan: speed, then shapes (2026-11-06, the user's go-ahead)

**The target:** the `solids` scene full screen at 60 (16.7 ms a frame, all of it: the loop's own
work too), measured after each change, kept or dropped by what it measures (`render.solids`, the
example's counters, `tools/bmds-prof`).

1. **The frame's fixed costs, in the example's use of the loop:** `BMDS_GAME_REPAINTS` with the
   whole canvas repainted (the loop no longer brings the buffer up to date: a 230 KB copy a frame
   for a program that redraws everything), and the clear by the 2D-DMA (`bmds_game_dma_fill`).
2. **Light only what shows:** Gouraud's vertex lighting done on demand, for vertices of triangles
   that survive culling (a generation stamp a vertex), not all of them.
3. **PIE for L8 Gouraud spans** (16 pixels a step), with a scalar twin, `simd test`.
4. **Internal RAM for the hot scratch** (vertices, the queue) when it fits, measured against PSRAM.
5. **The wire regression** from step 2 (projecting every vertex up front).
6. **Two cores** (§7), only if 1-5 leave the target missed.
7. **Shapes:** torus knot, cylinder, cone, icosphere, an extruded 2D polygon (logos).

## 12c. Step 3 continued: the vertex work (2026-11-06, the user's go-ahead)

1. **A smaller stored vertex** (`bmds_3d_placed_t`, 28 bytes against 52): view-space position,
   shade, screen position and outcode. Clip-space coordinates are needed only to clip (a few
   triangles, a few segments): recomputed then from the mesh's position (21 multiply-adds), not
   stored for every vertex. Measured A/B over launches (`render.solids`, `render.wire`).
2. **Both cores on the vertex work:** solids' draws are recorded at `bmds_3d_draw()` (matrices,
   lights, fog and the material copied; the mesh referenced) and done at `bmds_3d_end()`: every
   draw's vertices in one array, half placed by each core; then each core queues half of all the
   triangles into its own end of the queue; then the sort (once) and the bands as now. **API
   change, documented:** a solid's mesh is read at `bmds_3d_end()`, so it must stay as it was
   until then (wire and points still draw at once). When a frame's triangles could overflow the
   queue, or the vertices the array, the draws go one at a time as before.

## 12d. Step 5 design: models, the `.bm3d` format (2026-11-07, the user's go-ahead)

**Decisions (the user's):** a binary format first, not OBJ parsed on the board: the PC does the
costly work (parsing, welding, normals, edges) once, and loading is a read and a check. The format
plans for textures and several meshes a file even before they are all built.

**Why its own format:** the arrays are laid out as `bmds_3d_mesh_t` reads them (floats, uint16
indices), so a loaded mesh points into the file's own memory: no conversion, no second copy. A
576-triangle teapot with edges is about 20 KB.

### The file (on-disk ABI: frozen once shipped; `bmds/3dfile.h`)

Little-endian; floats are IEEE-754 binary32. A header, a table of sections, the sections:

| Offset | Field | |
|---|---|---|
| 0 | `char magic[4]` | `"BM3D"` |
| 4 | `uint16 version` | 1. A reader refuses a higher one (`BMDS_ENOTSUP`); additions are new sections and appended fields, not versions. |
| 6 | `uint16 header_bytes` | Where the section table starts (24 now; at least 24, a multiple of 4). |
| 8 | `uint32 file_bytes` | The file's length. |
| 12 | `uint32 section_count` | |
| 16 | `uint32 flags` | None yet. Bits a reader doesn't know: refused. |
| 20 | `uint32 reserved` | 0. |

A section's entry (16 bytes): `uint32 type`, `uint32 flags`, `uint32 offset` (from the file's
start; writers align sections to 16, readers need 4), `uint32 bytes`. `BMDS_3D_SECTION_REQUIRED`
(flag bit 0): a reader that doesn't know the type refuses the file (`BMDS_ENOTSUP`); without it an
unknown section is skipped. Every section's body starts with `uint32 size`: the bytes of its fixed
part, which may grow by appended fields (a reader reads those it knows and skips the rest; a size
below version 1's is refused). Offsets inside a section are from the section's start.

Section types (numbers never reused):

| Type | | Status |
|---|---|---|
| 1 `MESH` | One mesh (below). | v1 |
| 2 `NAMES` | Names for other sections. | v1 |
| 3 `TEXTURE` | An image. | reserved, drafted |
| 4 `MATERIAL` | How a mesh is drawn. | reserved, drafted |
| 5 `NODE` | A transform in a hierarchy. | reserved |

**`MESH`** (fixed part 64 bytes): `size`, `flags` (none yet; unknown bits refused, so a later
packed form can't be misread), `vertex_count` (1-65,535), `triangle_count`, `edge_count`,
`material` (an index among the file's `MATERIAL` sections, `0xffffffff`: none), `float bounds[4]`
(centre and radius), then the offsets of `positions` (3 floats a vertex; required), `normals`
(3 floats, unit; 0: none), `uvs` (2 floats; 0: none), `triangles` (3 uint16; 0 only with no
triangles), `edges` (2 uint16; 0 only with no edges) and `edge_faces` (2 uint16 an edge, a triangle
or `0xffff`; 0: none). Arrays 4-aligned, inside the section.

**`NAMES`** (fixed part 8 bytes): `size`, `count`; then `count` entries of `uint32 type`,
`uint32 index` (the nth section of that type, in table order) and `uint32 name` (the offset of a
UTF-8 string, NUL-terminated inside the section).

**`TEXTURE`** (drafted; fixed when first built): `size`, `flags`, `format` (`BMDS_PIXEL_L8` first),
`width`, `height`, `stride` (powers of two: the rasterizer wraps by mask), `pixels` (offset; 0:
not embedded), `palette` (offset of 256 `0x00RRGGBB`; 0: none), `path` (offset of a file name
relative to the model's, for a texture kept outside; 0: none). Carrying its palette, a texture can
be installed with it or remapped into the program's range (`bmds_canvas_remap`'s tables).
**`MATERIAL`** (drafted): `size`, `flags`, `mode` and material flags as `bmds_3d_material_t`,
`rgb`, `texture` (an index; `0xffffffff`: none).

### The SDK's calls (appended to `bmds/3d.h`)

```c
int  bmds_3d_model_load(const char *path, uint32_t mem_flags, bmds_3d_model_t **model);
int  bmds_3d_model_load_memory(const void *data, uint32_t bytes, bmds_3d_model_t **model);
uint32_t              bmds_3d_model_mesh_count(const bmds_3d_model_t *model);
const bmds_3d_mesh_t *bmds_3d_model_mesh(const bmds_3d_model_t *model, uint32_t index);
const char           *bmds_3d_model_mesh_name(const bmds_3d_model_t *model, uint32_t index);
int32_t               bmds_3d_model_find(const bmds_3d_model_t *model, const char *name);
void                  bmds_3d_model_free(bmds_3d_model_t *model);
```

- `load` reads the file into one allocation (`mem_flags`: `BMDS_MEM_FAST` puts vertices in
  internal RAM); `load_memory` uses the caller's bytes in place (4-aligned, kept until freed: a
  model built into the program's read-only data). The model's own record is one small allocation.
- **Checked as if hostile** before anything points into it: the header, every section inside the
  file, every array inside its section and aligned, every triangle's and edge's index below the
  vertex count, every edge's face below the triangle count, names terminated, every float finite
  (normals and uvs become texel addresses), the bounds' radius not below 0. The rasterizer trusts indices; a bad file is an error (`BMDS_EILSEQ`), never
  a crash. Fuzzed on the host (truncations, flipped bytes, random offsets).
- Textures and materials come later as `bmds_3d_model_texture()` and `bmds_3d_model_material()`,
  textures in an allocation of their own (texels in internal RAM where they fit, vertices not).

### `bmds-mesh3d` (`sdk/tools/mesh3d/`, C, built with the host's compiler)

`bmds-mesh3d [options] -o OUT.bm3d INPUT...`: each input an OBJ (`o` and `g` groups become named
meshes; `--merge` makes one) or Bézier patches (`.bpt`: a patch count, then each patch's `3 3` and
16 control points, rows of u; the front is where ∂P/∂u × ∂P/∂v points).

- OBJ: `v`, `vt`, `vn`, `f` (negative indices, polygons fanned); a vertex per distinct (position,
  uv, normal); without normals, smooth ones within a crease angle (`--crease`, default 60°).
- Patches: `--detail N` (an N × N grid a patch; 32 patches: 2·32·N² triangles less those with no
  area where a patch pinches), normals from the derivatives (moved a step inside where one
  vanishes), vertices welded across patches where position and normal agree.
- `--up z` (Z-up modellers into our Y-up), `--fit` (centred, radius 1), `--scale`,
  `--no-normals`, `--no-uvs`, `--no-edges`.
- Edges and bounds by libbmds3d's own `mesh.c` (`bmds_3d_mesh_edges()`, `bmds_3d_mesh_bounds()`),
  compiled into the tool: what a file stores is what the board would compute.
- In C so it can be built on the board later (self-hosting); the host tests compile its parsers and
  writer, and round-trip every file through the loader.

### The teapot

Newell's patches as freeglut carries them (`fg_teapot_data.h`, MIT; from Juhana Kouhia's archive
of Philip Schneider's data, 1990): 10 patches with a bottom, rotated into four quadrants or
mirrored into two, which make the classic 32 (`tools/teapot-bpt` writes them as `.bpt`; mirrored
copies get their rows reversed so every front faces out). Generated at `--detail 3` (≈ 576
triangles, half facing the camera) and 4 (≈ 1,024) to measure before a scene chooses. As built it
is 38 patches, made for drawing without back faces or a depth buffer (§13, step 5).

## 13. As built

### Step 1: math and wireframe (2026-11-06)

- **`sdk/include/bmds/3d.h`, `sdk/3d/`** (`libbmds3d.a`, linked by `bmds_add_program` and
  `bmds-cc` after libbmdsgame): `math.c` (the matrices), `mesh.c` (shapes, edges, bounds),
  `context.c` (contexts, the stack, culling, drawing meshes, projecting, sorting, counters),
  `wire.c` (segments and points). 15.8 KB of text in all (math 2.2, meshes 5.4, contexts 4.6,
  wire 3.6); a program links only the objects it uses.
- **As designed in §4, with these settled:**
  - The vertex scratch is the context's only memory (28 bytes a vertex, 4,096 by default:
    112 KB; `BMDS_MEM_FAST` falls back to PSRAM when internal RAM can't hold it).
  - **Edges:** vertices at one position are welded (a hash on the positions' bits), the
    triangles' sides sorted (an LSD radix sort on the welded pair), each run one edge with its
    first two triangles. Made shapes **mark their quads' diagonals** as they make them (exact: a
    sphere's or torus's quads aren't planar, and a grid's lines and diagonals are both between
    coplanar triangles); where one of a quad's triangles has no area (a sphere's poles) the
    other's "diagonal" is a real edge and isn't marked. A caller's mesh gets the heuristic:
    dropped between coplanar triangles when it is the longest side of both, or every coplanar
    edge with `BMDS_3D_EDGES_COPLANAR` (a fan, a cap). `owned_edges` beside `owned`, so a made
    mesh's edges can be rebuilt without freeing its geometry.
  - **Hidden lines** (`BMDS_3D_CULL_BACK` on wire): an edge is drawn when either triangle beside
    it faces the viewer, tested in view space (`n · p < 0`; looking down −Z for an orthographic
    projection), so it works with the eye inside the bounds and through near clipping. Exact for
    convex meshes; a torus shows its inner far side, as expected without a depth test.
  - **Segments:** near and far clipped in clip space (Liang and Barsky), projected, clipped to the
    viewport within the canvas's clip, then stepped along the major axis in 16.16 from the exact
    sub-pixel ends: the pixels whose centres the line passes, each end's pixel included, the
    minor coordinate clamped to the ends' rows (no stray pixel past an end). The shade is
    stepped beside it, so a line going away fades along its length.
  - **Shades:** one table of pixel values a draw (`bmds_3d_ink_t`): the ramp's entries on L8,
    32 levels of `rgb` towards black on RGB565 and BGR24, so the inner loops are the same for
    every format.
  - **Points** are `point_size` squares, centred, culled by the clip volume.
  - Fog defaults to 1-100; `bmds_3d_stats()` counts meshes, culled meshes, vertices, lines,
    points and pixels since `bmds_3d_begin()`.
- **Host tests** (`tests/host/3d.cpp`, 9 cases, 12,809 assertions): the matrices against worked
  values, GLU's perspective and look-at; made meshes' edge counts (cube 12, grid 2n(n+1) with
  4n open, sphere's meridians and parallels with the seam welded, torus closed) and outward
  faces; a caller's square and hexagon fan; lines on exact pixels (horizontal, diagonal, a
  strip), damage; clipping in all three formats, with 4,000 random huge lines, orthographic and
  through the eye, and a NaN, never writing outside the clip; near clipping; points; shading by
  distance on L8 and BGR24; a wire cube's 12 edges, 4 head-on and 9 at a corner with hidden lines,
  culled whole behind the camera; `ENOSYS`, `ENOSPC`, bad flags; the stack; projecting and
  sorting; no allocation left (`FakeMemory`, the host's `mem_alloc` and `mem_free`, now in the
  fake system call table libbmdsgame's tests use).
- **`sdk/examples/wire`**: the stars, a cube, a torus and an orbiting sphere at 640×360 L8, the
  mouse turning the camera, the wheel moving it, Space for hidden lines, `-F` full screen, `-e`
  nothing but the clear (what presenting costs). Checked on the board, windowed and full screen.
- **`render.wire` in `benchprog`** (`benchprog wire`), the board, 640×360 L8 in PSRAM:

  | Case | ms a frame |
  |---|---|
  | cube, torus (32×12), sphere (12×8), hidden lines | 2.37 |
  | the same, all 960 edges | 3.17 (3.3 µs an edge) |
  | 2,000 points, shaded | 1.90 (0.95 µs a point) |

  §10's target of 5,000 edges a frame needs about three times this; the time is mostly per edge
  (clipping and projecting each end again, the shade, the face tests), not per pixel. Projecting
  each vertex once into the scratch and reusing it, and the face tests cached per triangle, come
  with step 2's queue.
- **Found: presenting is the limit, not drawing.** `wire` runs at 35-37 fps windowed or full
  screen, drawing in 7-8 ms; `wire -e` (a clear and the counters, 3 ms) runs at 38-39. A
  640×360 L8 surface damaged whole every frame presents at under 40 a second (games.md's
  measurements agree: 39 for RGB565 at 2× full screen, damaged whole). The demo draws whole
  frames, so this is the first thing it needs from the kernel (`demo.md` §8a). Fixed the same day
  (`demo.md` §8b, `games.md` §27): `wire -F` now runs at 60.

### Step 2: solids (2026-11-06)

- **As designed in §12a**, with these settled on the way:
  - **New files:** `solid.c` (records, lights, clipping, the queue, the sort) and `raster.c`

  - **Each vertex is placed once a draw** (`bmds_3d_screen()`: its outcode against near, far and the

    all three inside is wound, culled and queued from those; only the rest are clipped (Sutherland
    and Hodgman, up to 9 vertices, fanned). Segments whose ends are between near and far reuse the
    positions too.
  - **Back faces go before they are lit** (the winding from the 28.4 positions).
  - **Flat lighting faces the viewer:** the face normal is turned to the side the viewer sees, so an
    uncull'd back face is lit as its front (two-sided) and a mirroring projection (the host tests'

  - **Gouraud steps by the plane's x gradient** (once a triangle, held in range for slivers); each
    span evaluates its start only, and re-steps with one integer division only when rounding would
    leave the ramp at its last pixel.
  - **The order (found on the board):** sorting every triangle by its mean depth let a large cube
    face's triangle sort after torus triangles in front of it: red specks on the torus. Now by
    default each draw's triangles stay together, the draws far to near by their bounds' centre

    other.
- **Host tests** (`tests/host/3d.cpp`, 15 cases, 43,024 assertions; `palette.cpp`): the fill rule

- **`sdk/examples/solids`:** a flat cube, a Gouraud torus, a faceted and a smooth sphere over a wire
  floor; the light from the pointer, Space flat or Gouraud, `-f 565|888`. Checked on the board in

- **`render.solids` in `benchprog`** (a 2,304-triangle torus, ~1,060 facing, ~47,000 pixels, 640×360
  L8 in PSRAM, the board):

  | | first build | now |
  |---|---|---|
  | flat | (32 ms a frame in `solids`) | 9.5 ms |
  | Gouraud | | 11.7 ms |

  Profiled (core 1, `tools/bmds-prof`): the first build spent its time in 64-bit division calls,
  `rintf` (a library call), a plane function called 18 times a triangle and copies of polygons; now

### Step 3 so far: speed, shapes (2026-11-06)

- **How to measure (learned the hard way):** the same `benchprog` binary differs by up to ~1 ms
  (10%) from one launch to the next, pinned or not (where its buffers and code land in PSRAM),
  while runs within a launch agree to ~2%. A single launch each made several changes look ±0.5-1
  ms better or worse than they are. Comparisons are now A/B builds alternated over several
  launches, pinned (`core=`, added to `render.wire` and `render.solids`), and averaged. Measured
  that way, the changes below that this section doesn't credit with a figure are within the noise.
- **Kept, measured:**
  - **Two cores** (`bmds_3d_config_t.cores` = 2, `cores.c`): a helper thread pinned to the other
    core draws the sorted queue's rows from a split down while the caller draws above it; the split
    moves each frame towards equal times (the other core has the presenter or the window manager).
    The cores share one L1 data cache, so the canvas needs nothing written back between them. Host
    test: two cores draw the one core's pixels exactly over 6 frames. `render.solids` pinned, 2
    launches each: Gouraud 12.3 → 10.1 ms, flat 10.0 → 8.9 ms.
  - **The vertices in internal RAM** (`mem_flags` `BMDS_MEM_FAST`): ~1.1 ms (10%) on
    `render.solids` over 3 launches each. **But** in `solids` full screen it left the kernel too
    little internal RAM: the program then held ~105 KB of it (a 32 KB stack, 45 KB of vertices,
    libbmdsgame's), the largest free block fell to 38 KB, and entering full screen failed (out of
    memory: the presenter's 30 KB strip and the surface's lines and descriptors). The queue went
    back to PSRAM; `mem_flags` now applies to the vertices only, documented as competing with the
    kernel; the example doesn't use it. Worth a kernel look: full screen could fall back to a PSRAM
    strip rather than fail.
  - **The example's frame:** `BMDS_GAME_REPAINTS` with the whole canvas repainted (the loop no
    longer brings each buffer up to date: a 230 KB copy) and the clear by the 2D-DMA.
- **Kept, not shown to matter by the bench** (within the noise; sensible in themselves):
  Gouraud's vertices lit on demand (only those of triangles drawn); lines' loops without per-pixel
  clamps and, unshaded, without a shade; one 4-pass sort a frame (the draw's rank and the
  triangle's depth in one key, not 8 passes); the Gouraud plane in integers from the top vertex.
  **A slip found on the way:** the first integer plane converted floats to 64-bit integers, which
  this core does in software through doubles (`__fixunssfdi`, `__muldf3`): 3-4 ms worse. Now only
  float-to-int32 conversions; `__divdi3` (an edge's rare large numerator) is the library's only
  64-bit helper left.
- **PIE spans: not done.** Triangles here average ~45 pixels; the profile is per-row and
  per-triangle overhead, and the Gouraud pixel loop is ~0.5 ms of a frame. Later, if pixels come
  to matter (bigger triangles, textures).
- **Shapes** (`BMDS_3D_SHAPE_CYLINDER`, `_CONE`, `_ICOSPHERE`, `_TORUS_KNOT` with `p`, `q` appended
  to the shape; `bmds_3d_mesh_extrude()` for a simple polygon, ear-clipped caps, either winding):
  caps' and extrusions' inner sides marked so wire shows outlines; host-tested (closed meshes,
  Euler's counts, outward faces, the L-shape's cap area, bad input); `solids`' S key shows each.
- **Where the target stands** (`solids` full screen, two cores): ~1,100 triangles over the floor
  draw in ~20 ms (40 fps); with the middle shape lighter (~400-500 triangles) 15-16 ms of drawing,
  17-19 ms a frame (50-55 fps). What's left on the caller's core is mostly fixed: the floor's 544
  lines (~3 ms), every vertex transformed and placed (~2.7 ms: ~570 cycles a vertex, mostly
  writing and reading the 44-byte vertex records in PSRAM), queueing (~3.4 ms). Next levers: a
  smaller vertex record (clip coordinates only for what clips), the helper also transforming and
  queueing half the draws, and the scene itself (a demo part sized to its budget).

### Step 3, the vertex work (§12c): both tried, both measured, both reverted (2026-11-06)

A/B against the committed library, `render.solids` pinned to core 0, three launches each:

| Change | One core | Two cores |
|---|---|---|
| A 28-byte stored vertex (clip space worked out again only to clip) | +1.0 ms (slower) | +0.6 ms |
| The helper placing half a draw's vertices and queueing half its triangles | +0.55 ms | −0.3 ms (3%) |

- **The smaller record was slower:** the 52-byte records in PSRAM weren't the cost; building a full
  vertex and copying what's kept (and filling two for each wire segment) was more than the writes
  saved. The profile's "time in the vertex pass" said where time went, not what would shrink it.
- **Splitting the vertex work barely helped:** placing vertices and queueing triangles are memory
  work, and the P4's two cores share one L1 data cache (`docs/platforms/esp32p4.md`): they
  contend rather than add up. Rasterizing, more work a byte, did scale (12.3 → 10.1 ms). The
  restructuring also cost the single-core path 5%. Not worth its complexity.
- **Kept:** a host test of two cores with a queue too small for a draw (the same triangles counted,
  nothing lost), and `benchprog`'s shapes initialized for the appended `p` and `q` (a `-Werror`
  build would have failed).
- **Where that leaves 60 for the `solids` scene:** the library is close to what this design does on
  this chip. What remains is the scene: its 544-line floor (~3 ms), ~1,100 triangles, the text.
  The lighter scenes (400-500 triangles) are at 17-19 ms a frame. The demo's parts will be sized
  to the budget with the frame-time overlay; larger levers, if a part needs them, are a different
  design (bands drawn in internal RAM and copied by DMA, or a smaller canvas for the 3D parts),
  each a measured experiment first.

### Step 3, the two experiments (2026-11-06, the user's choice before the demo)

Bounds measured first (`render.solids`, `w=`, `h=`, `canvas=internal` added; pinned, alternated,
two launches each):

1. **Bands through internal RAM: not built.** Its best case is the whole canvas in internal RAM.
   At 640×144 (92 KB, what internal RAM holds) internal was no faster than PSRAM: Gouraud 8.2
   against 8.0 ms, flat 7.4 against 7.3. Writing pixels into PSRAM isn't a cost worth avoiding;
   bands would only add each band's triangle set-up and the copies.
2. **A smaller canvas:** 320×180 (a quarter of the pixels), the same scene:

   | | 640×360 | 320×180 |
   |---|---|---|
   | one core, Gouraud / flat | 12.3 / 10.0 ms | 9.0 / 8.1 ms |
   | two cores, Gouraud / flat | 9.8 / 8.6 ms | 7.5 / 7.1 ms |

   **`solids` full screen at 320×180 runs at 60** (`-s 320x180`: 12.9 ms drawing, 16.8 ms a
   frame, the full ~1,100-triangle scene; 45 fps at 640×360 in the same run). Scaled 4× it is
   chunky: the 320×200 era's look.
- **What this says:** with almost no pixels the torus still costs ~7 ms: ~1,100 cycles an input
  triangle, the fixed cost of a triangle (outcodes, culling, lighting, queueing, sorting, three
  edges' set-up with integer divisions, rows' overhead), not pixels and not memory. The lever
  left inside the library is that cost: edges stepped from a float reciprocal instead of integer
  divisions (still exact where it matters: a shared edge stepped the same way by both triangles),
  fewer per-row checks. Its own measured step, if wanted.

### Step 3, the per-triangle work (2026-11-06, the user's choice)

Profiled at 320×180 (pixels hardly matter there), then by source line (`-g`, `addr2line` over the
samples): `queue_solid` 29%, triangles 25%, edge set-up 11%, the vertex pass 17.5%, the sort 6%.
The lines' samples gather on loads (vertex records' outcodes and positions) and 64-bit products,
where the core waits, so they say where it waits more than what costs. Each idea A/B'd against
the committed library over launches, pinned:

| Change | 640×360 Gouraud / flat | 320×180 Gouraud / flat | Kept |
|---|---|---|---|
| Edges from a float slope stepped in integers (no divisions), 32-bit cross products | ±0 / +0.15 ms | −0.2 / −0.1 ms | yes: simpler, no divisions, the same speed |
| The torus's arrays in internal RAM (`meshfast=1`) | +0.2 / +0.2 ms | | no (nothing to keep: a bench switch) |
| The vertex records in internal RAM (`fast=1`, from earlier) | −1.0 / −1.1 ms | | as before: optional, competes with full screen |

- **The new edges keep the fill rule exact where it matters:** stepping adds integers, so an edge's
  x on a row is the same whichever row the stepping began on, and both triangles on a shared edge
  step it top to bottom from the same two ends with the same float slope. The fill-rule tests (a
  fan, a jittered grid: every pixel once) pass unchanged.
- **What this says:** the per-triangle cost (~1,100 cycles an input triangle at 360 MHz) is spread
  over many small steps (outcodes, culling, lighting, the record, the sort, three edges, the rows)
  with no single one left to remove; only the vertex records' memory moves it (~9%). The 128 KB L2
  cache (`CONFIG_CACHE_L2_CACHE_128KB`) is shared by everything in PSRAM; a larger one would cost
  the kernel internal RAM it doesn't have to spare.
- **For the demo:** a 3D part at 640×360 holds 60 with ~400-500 triangles; at 320×180 with ~1,100
  (`solids -s 320x180`). The demo can choose per part.

### Step 4: textures (2026-11-07)

Built to §4d, §4f step 7 and §5a, L8 only (the textured modes return `-BMDS_ENOSYS` on RGB565 and
BGR24 until step 6). Measured on the board (`bench run render.textured`, core 0, the 2,304-triangle
torus, 47,379 pixels a frame; `render.solids` beside it: flat 9.8 ms, Gouraud 11.7, on core 1):
textured 15.2 ms, perspective 18.5, lit flat 16.4, lit Gouraud 18.7 (perspective 22.0), envmap
15.9; a light table 36 ms (a scene's start, not a frame's); a full-screen rotozoom 9.2 ms, a remap
14.6. Texturing costs ~100 ns a pixel over flat; demo1's finale draws its rotozoomer a texel each
2×2 pixels (as its tunnel) for 9.5 ms a frame, its 128×128 texture 16 KB for the shared L1.

- **The modes** (appended to `bmds_3d_material_t::mode`): `BMDS_3D_TEXTURED` (unlit: the texel
  itself, or through the light table at full light, which makes the table a remap; with `DEPTH_CUE`
  fogged per vertex), `_TEXTURED_FLAT` (lit per triangle, as `FLAT`), `_TEXTURED_GOURAUD` (lit per
  vertex by the mesh's normals, on demand as `GOURAUD`; without normals per triangle), `_ENVMAP`
  (the uvs from each vertex's view-space normal, x and y across the texture: a sphere map, "matcap";
  unlit as `TEXTURED`; without normals the triangle's own). `BMDS_3D_PERSPECTIVE` (a flag): exact
  every 16 pixels, affine between; without it affine across the triangle (the PS1's swim).
- **The material grew at its end** (`texture`, `light_table`). `bmds_3d_check_material()` now takes
  any `size` from the old struct's (up to `point_size`) on, and `bmds_3d_draw()` reads a copy with
  what the caller's size leaves out as zero; a host test draws with the old size and gets the same
  pixels. Textures: L8, width, height and stride powers of two (stride at most 65536, so the row's
  offset is `(v >> (16 − log2 stride)) & ((h − 1) << log2 stride)`: no multiply); read at
  `bmds_3d_end()`, so they must stay until then (documented). Lit modes and `DEPTH_CUE` need a light
  table (`-BMDS_EINVAL` without), `TEXTURED*` need the mesh's uvs, `ENVMAP` doesn't.
- **Memory:** a textured triangle's coordinates (u, v in texels, 1 / w; 36 bytes) sit in an array
  beside the queue, allocated at a context's first textured draw (`max_triangles` × 36: 72 KB of
  PSRAM by default), so programs without textures pay nothing. The record (one a draw) gained the
  texture's pointer, masks and sizes. The vertex record is unchanged (§13's lesson: its size costs).
- **The triangles** (`texture.c`): the same edges as `raster.c` (moved to `3d_internal.h` as inline
  functions, so both step them identically: the fill rule holds between textured and plain
  triangles, tested on a jittered grid and a near-clipped torus in every mode). Per triangle, float
  planes for u, v (u / w, v / w, 1 / w with perspective) and the shade, from the top vertex; u and v
  moved by whole turns of the texture to near zero first, so 16.16 holds any tiling. Per span, the
  start evaluated (three multiply-adds a plane) and converted once; per pixel only integer adds,
  masks and loads. Perspective: one float division per 16-pixel run (`1 / q`), a table of
  reciprocals for the last run's length. Clipping (Sutherland and Hodgman) carries u and v too, in
  clip space, so they stay right through near clipping.
- **Spans:** three loops (texels straight; one light-table row a triangle; a row per pixel from the
  shade, `table[((s >> 8) & 0x1f00) | texel]`, branch-free and inside the 8 KB table whatever s is),
  each unrolled by four with the four texels gathered into one 32-bit store once aligned. A run's
  fields are copied to locals first: a byte store may alias anything, so the compiler would reload
  them after each one. No PIE: gathers don't vectorize (§6).
- **The shade's range:** 32 shades (`BMDS_3D_LIGHT_SHADES`), shade 31 the texel's own colour; a
  span's shade held in 0.5..31.5 as Gouraud's (re-stepped by one division only when rounding would
  leave it).
- **Light tables** (`bmds_3d_light_table(table, palette, first, count, dark)`, `light.c`): 32 × 256,
  each entry the palette index nearest the texel's colour at that shade, from `dark` (black, or a
  fog's colour) at 0 to the colour at 31; candidates only `first..first + count − 1` (programs
  reserve entries). Nearest by the image loader's weights (3, 4, 2). Exact, not a 32³ cube: the
  candidates sorted by weighted brightness `3r + 4g + 2b`, each search starting at the colour's own
  brightness and going outwards until the brightness difference d can't be beaten (Cauchy and
  Schwarz: a weighted distance is at least d² / 9), and a 256-entry cache of colours found (dark
  shades repeat). Host-tested against brute force over four palettes and ranges; its time on the
  board is `light_table_ms`.
- **libbmdsgame** (`texmap.c`): `bmds_canvas_image()` (a canvas, or a rectangle of it, as an
  image: last frame as a texture), `bmds_game_affine_t` and `bmds_canvas_texture_affine()` (an
  affine map with wrapping, 16.16: rotozoomers, floors a row at a time; L8 four pixels a store,
  RGB565 two, with the stride a power of two; any stride and BGR24 by a multiply), and
  `bmds_game_affine_rotozoom()` to set one from a centre, an angle and a zoom; `bmds_canvas_remap()`
  (a uint16 (u, v) table a pixel plus a moving offset: tunnels, lenses), which fell out cheaply.
  Host-tested in every format against a pixel at a time (`tests/host/texmap.cpp`).
- **The examples:** `solids -t` or T steps through textured (a procedural checker of glowing tiles,
  lit per vertex, perspective-correct), chrome (`ENVMAP` with a made-up sky and ground) and unlit
  affine; the light table built once from the palette (all but the background, text and floor).
  `benchprog textured`: the 2,304-triangle torus of `render.solids` in each textured mode, a light
  table built, a 640×360 rotozoom and tunnel remap (`tex=`, `texfast=1`, `cores=`, `core=`, `w=`,
  `h=` as the other cases).
- **Host tests:** `tests/host/3d.cpp` now 25 cases, 162,232 assertions: textured triangles cover
  exactly the flat ones' pixels in every mode, affine and perspective (a jittered grid; a torus
  through the near plane); wrapping both ways, a stride wider than the texture, a quad far past the
  guard band clipped with its uvs; a floor through the near plane perspective-correct within a texel
  of ray-cast truth; light tables against brute force (four ranges and dark colours); lighting through
  the table (full light the texel itself, none black, half within a shade), fog, chrome on a sphere;
  old-size materials drawing the same pixels; what textured materials need (`EINVAL`, `ENOSYS`); two
  cores with a flushing queue pixel for pixel. `tests/host/texmap.cpp`: 4 cases, 23,171 assertions.
- **Left for later:** the z-buffer (§4e: not trivial to do well, and the painter's order serves the
  demo; its own measured step), textured `ADD`, RGB565 textures (step 6), PIE for anything here,
  ENVMAP's normals transformed once a vertex rather than once a triangle's use (they're worked out
  for each triangle that uses a vertex; caching them would grow the vertex record or need another
  array), mipmaps (a far texture shimmers), and the board's figures for all of it.

### Efficiency pass: where the time goes, and PIE (2026-11-07, the user's go-ahead)

The user asked whether a SIMD refactor would pay. Measured first: the torus at 640×360 and at
320×180 (the same triangles, a quarter of the pixels), pinned to core 0, so the difference is the
pixels' part and the rest the triangles':

| | 640×360 | 320×180 | per triangle (no pixels) |
|---|---|---|---|
| flat | 9.75 ms | 7.60 | ~6.9 ms (71%) |
| Gouraud | 11.76 | 8.47 | ~7.4 |
| textured | 15.3 | 10.55 | ~9.0 |
| textured, perspective | 18.6 | 12.07 | ~9.9 |

- **PIE doesn't fit, so no SIMD refactor:** the torus's triangles average ~45 pixels, its spans ~7,
  so 16-byte steps would hardly start (and a canvas in internal RAM was no faster: writing pixels
  isn't the cost); every textured mode is a gather (a texel, then a light-table entry), which PIE
  can't do; vertices are floats, which PIE doesn't have. Where it would pay later: Gouraud spans of
  16 pixels or more (close-ups), the z-buffer's test, `ADD`.
- **What "pixels" cost is mostly rows:** ~22 cycles a pixel flat is a row's work (edges, clamps, a
  call, `memset`'s own) spread over its few pixels.
- **Code in internal RAM** (the user's question): no. Code in PSRAM runs as fast as in internal
  RAM once cached (`programs.md` §2), each core's 16 KB instruction cache is its own and holds
  these loops, and the internal heap isn't executable.

Changed, each A/B against the committed library (three rounds alternated, core 0; at 320×180 and
with two cores, two rounds):

| | before | after | 320×180 | two cores |
|---|---|---|---|---|
| flat | 10.34 ms | 9.11 (−12%) | 7.74 → 6.97 | 8.66 → 8.02 |
| Gouraud | 12.39 | 10.07 (−19%) | 8.49 → 7.51 | 9.83 → 8.40 |
| textured | 15.34 | 14.02 (−9%) | 10.49 → 10.01 | 11.47 → 10.80 |
| textured, perspective | 18.60 | 14.22 (−24%) | 12.04 → 10.20 | 13.15 → 10.90 |
| textured flat | 16.51 | 15.29 (−7%) | | |
| textured Gouraud | 18.79 | 17.57 (−7%) | | |
| textured Gouraud, perspective | 22.07 | 17.82 (−19%) | | |
| envmap | 15.99 | 14.70 (−8%) | | |
| a light table | 36.3 | 27.7 (−24%) | | |

- **Perspective only where it shows:** a triangle whose 1 / w at its vertices goes from q_min to
  q_max moves a point by at most (q_max / q_min − 1) / 4 of the way between them when drawn
  affine; times its texels across, under a quarter texel it is drawn affine (most of a far or
  small triangle's: the torus's nearly all). Large, near ones (the floor test through the near
  plane) stay exact every 16 pixels.
- **Textured spans set up in integers:** u and v at the top vertex's pixel in 16.16, then by whole
  pixels with wrapping 32-bit arithmetic (16.16 wraps at 65,536 texels, a multiple of any texture's
  size, so any distance is exact for the masks); the shade the same way in 64 bits. Was: three
  planes evaluated in floats a span, each converted with clamps. Each triangle's whole turns by a
  multiply (`1 / tw`, exact) instead of two divisions.
- **Edges in 32 bits** (unsigned, wrapping): inside the guard band an edge's x on any row it covers
  fits (±32,768 pixels); only the step past an edge under a pixel tall can wrap, and isn't used. The
  fill rule's tests pass unchanged.
- **L8 rows in their own loop:** no format checks a row, flat spans of under 32 bytes written
  inline (bytes to a word boundary, then words), and the Gouraud plane in 32 bits when it can't
  overflow over the triangle's box (|gradient| × size under 2^29), else 64 as before.
- **The sort:** the four bytes' counts in one pass over the keys (16-bit counts, 2 KB of stack),
  and a byte the same in every key skipped (the rank's top byte, always, by draws).
- **Light tables:** two plain loops (up from the colour's brightness, then down) instead of one
  choosing the nearer side each step: a fifth more candidates compared, 24% less time (the
  benchmark's palette: 7,934 searches, ~28 candidates each). Tried first and dropped: starting from
  the texel's answer a shade darker (6% slower: the bound comes from the true nearest whatever the
  start). **Found on the way:** the search stopped at a candidate exactly on the bound, which could
  tie; ties go to the lower index, and 22 of 200 random palettes got a higher one (equally near:
  invisible). Now compared; a host test with coarse palettes (repeats, ties) checks the lowest index.
- **`benchprog core=N` now always runs there** (`processes.md` §3.12a): it ran on the loader's core
  whenever that was the other one, printing "core -1", ~0.7 ms faster than core 0 (core 1 idle
  without the display), so earlier figures from a first launch may be core 1's. It now stops
  rather than measure elsewhere.

**Second pass (2026-11-07, the user's go-ahead), A/B, three rounds:**

- **ENVMAP's coordinates once a vertex:** a vertex's (u, v) from its normal is worked out the first
  time a drawn triangle uses it in a draw and kept (`envuv`, 8 bytes a vertex in PSRAM, allocated
  at the first ENVMAP draw with normals): 14.64 → 14.42 ms (−1.5%).
- **libbmdsgame's `bmds_canvas_remap()`:** L8 with a power-of-two stride takes the table two
  entries a load, u and v moved by byte-wise adds that can't carry across bytes, the row by a
  shift: 14.79 → 14.01 ms (−5%). The rest is the table: 460 KB read from PSRAM a frame at
  640×360. Host-tested with every byte value and moves past the top bit.

### Step 5: models, the `.bm3d` format (2026-11-07, the user's go-ahead; §12d)

- **The format** as designed: `bmds/3dfile.h` (header, section table, `MESH` and `NAMES`; `TEXTURE`,
  `MATERIAL` and `NODE` numbered and reserved). `sdk/3d/model.c`: `bmds_3d_model_load()` (one read,
  one allocation in the caller's memory), `_load_memory()` (in place), `_mesh_count()`, `_mesh()`,
  `_mesh_name()`, `_find()`, `_free()`. Refused before anything points into the file: anything
  outside the file or its section, misaligned, an index or face out of range, a name not
  terminated, a float not finite (NaN or infinity), a negative radius (`BMDS_EILSEQ`); a later
  version, a header or mesh flag, or a required section it doesn't know (`BMDS_ENOTSUP`).
- **`bmds-mesh3d`** (`sdk/tools/mesh3d`, C; `build-host/bmds-mesh3d`): OBJ (groups as named meshes,
  `--merge`, negative indices, polygons fanned, v flipped to rows, normals within `--crease`) and
  `.bpt` patches (`--detail`, normals from the derivatives, a pinch's found a step inside, seams
  welded within the crease), `--up z`, `--fit`, `--scale`, `--no-normals/-uvs/-edges`; bounds and
  edges by libbmds3d's `mesh.c` compiled in, less the sides inside a polygon (a patch's quad's
  diagonal, an OBJ polygon's spokes: `mesh.c` keeps those where the triangles bend, so a wire
  teapot showed every diagonal); the teapot's edges at detail 3, 833 → 650.

  freeglut spreads the knob's top by 0.002 (for GL's evaluators): its normal there came out
